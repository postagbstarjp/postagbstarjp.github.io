研究の方法・計算環境についての覚え書き · 2026年10月25日

RADMC-3Dの計算環境を選ぶための覚え書き

自宅PCで時間のかかる放射輸送計算を進めるための実務ノート

RADMC-3Dの計算がローカルPCでは長時間かかるとき、どの計算環境を選び、どのような順序で性能・費用・科学的妥当性を確認するかを整理します。

2026年10月25日時点の調査に基づく技術ノートです。クラウド上でのRADMC-3Dの性能・費用を実測した結果ではありません。

  • 未実測の調査ノート：性能と費用の比較実験ではありません。
  • まずローカルの並列化を確認する：ビルド条件と実際の計算時間を記録します。
  • 単一モデルと多数の独立モデルを区別する：前者は1件の所要時間、後者は一定時間に完了する件数が検討の軸になります。
問題設定：自宅PCで計算時間が長すぎる手元の環境からクラウドLinuxへ移す並列化：単一モデルと多数モデルは別問題候補となる計算サービス費用は「完成したモデル1件当たり」で比較する初回試験の進め方AIコーディング支援を使う範囲選択の目安参考資料

問題設定：自宅PCで計算時間が長すぎる

RADMC-3Dなどを用いて、星周エンベロープのダスト温度、スペクトルエネルギー分布（SED）、画像やスペクトルを計算する場合を考えます。計算格子が細かい、光子パケット数が多い、あるいは光学的に厚い領域を扱うと、一つのモデルの計算が長時間に及ぶことがあります。質量放出率、密度分布、ダストの性質、幾何構造などを変えたパラメータ探索では、独立したモデルを多数計算する時間も問題になります。

このようなときの選択肢は、手元のPCの設定を改善すること、大学・研究機関の計算機や共同利用HPCを使うこと、商用クラウドで必要な期間だけCPU計算資源を借りることです。本ノートでは、既存のRADMC-3D環境を可能な限り維持しながら、計算能力を拡張する方法を整理します。クラウド上での実測結果を報告するものではありません。

初めに区別すべき問題は二つあります。一つのモデルが終了するまでの時間を短くしたいのか、それとも多数のモデルをより早く計算し終えたいのか。この違いによって、必要なCPU構成やサービスは変わります。

手元の環境からクラウドLinuxへ移す

Windows上のWSL2／UbuntuでRADMC-3Dを使用している場合、最初の候補はクラウド上の単一Linux仮想マシン（VM）です。CPU数とメモリ容量を選び、SSHで遠隔ログインし、RADMC-3Dのソースを対象の環境でコンパイルして、モデルを実行します。入力ファイルの転送にはSCPやrsync、結果の回収にも同様の手段を使用できます。

作業の基本順序は、①ローカルのソースの版とビルド条件を記録する、②クラウドのUbuntuなどに同じ版の環境を用意する、③テストモデルだけを転送する、④出力と所要時間を比較する、⑤結果を回収して課金対象の資源を停止・削除する、というものです。VMの作成と利用には、通常、アカウント登録、決済設定、利用条件への同意、ネットワークとSSH認証の設定が必要です。

既存のLinux用RADMC-3Dをクラウド上で実行するために、最初からMPIプログラムを書き直す必要はありません。ただし、単に実行ファイルが動いたことだけでは、物理的な計算結果の検証は済みません。ソースのcommit、コンパイラ、オプション、入力、乱数条件を記録して比較します。

並列化：単一モデルと多数モデルは別問題

単一モデルを短時間で終了させる：RADMC-3Dの熱的Monte Carlo計算（mctherm）には、OpenMPで複数スレッドを利用する仕組みがあります。OpenMP有効のコンパイルを確認し、例えばradmc3d mctherm setthreads 4のように実行します。スレッド数を増やしても速度は比例して向上するとは限らず、計算内容、メモリ帯域、物理コア数、メモリ使用量を測定する必要があります。画像・スペクトル計算などは、使用するソースとビルド条件で並列化の対応状況を確認します。

多数の独立モデルを処理する：モデルごとに作業ディレクトリと入出力を分離し、複数のVMやバッチジョブへ割り当てます。独立したパラメータ探索では、単一ジョブの高速化よりも、一定時間に完了するモデル数（スループット）を改善しやすい場合があります。ただし、同時に使用する計算資源が増えるので、費用も確認します。

クラウドの「100 vCPU」は、100個の論理CPU実行単位を割り当てるという意味であり、100個の物理コアや100倍の高速化を保証しません。また、通常のRADMC-3Dを複数VMに分散配置しても、単一モデルが自動的にMPI並列化されるわけではありません。標準的なCPU版をGPUサーバーへ移すだけでも、GPUによる高速化は得られません。

候補となる計算サービス

以下は2026年10月25日に整理した候補です。単一Linux VMの利用と、大量の独立ジョブを管理するサービスは分けて考えます。料金、提供地域、CPUの種類、メモリ、利用枠、決済条件は利用時に各公式サイトで再確認する必要があります。

単一のLinux計算機を借りる場合

  • Google Cloud Compute Engine：CPU・メモリの構成を選択してLinux VMを利用できます。C4 highcpuの16〜32 vCPU級は、初回の性能比較候補です。より大きな構成にはクォータと費用の確認が必要です。
  • Alibaba Cloud ECS：中国国内を含むリージョンでCPU VMを利用する選択肢です。中国からの接続性と実際のCPU料金を確認して比較します。複数ノード運用にはE-HPC Nextもあります。
  • Hetzner Cloud：時間単位でLinuxサーバーを利用する候補です。共有CPU型は低予算の環境構築テストに使いやすい一方、高負荷の連続計算では専有CPU型との性能比較が必要です。

独立モデルを多数実行する場合

  • Google Cloud Batch：多数の独立タスクをVMへ割り当てて処理する仕組みです。ジョブ数が増えた段階の候補で、VMやストレージなどの使用料金が発生します。
  • Alibaba Cloud E-HPC Next：クラスタの構築・管理を支援します。サービス利用料と、実際に使用するECS・ストレージ等の資源料金を区別します。
  • Tencent Cloud THPC：HPCクラスタとジョブ管理の候補です。中国国内での契約・通信条件も含めてAlibaba Cloudと比較します。
  • AWS ParallelCluster：EC2などを使ってSlurmベースのHPC環境を構築する方法です。初回の単一VM実験よりも運用が複雑になります。
  • Microsoft Azure Batch／Azure CycleCloud：多数のタスクの処理、またはSlurm等のクラスタ管理に利用できます。所属機関に既存契約がある場合の比較対象です。

Google ColabやKaggle NotebooksはPythonの試作・解析には使えますが、長時間のCPU計算を安定して実行する用途には制約があります。AutoDLやRunpodなどのGPU中心のサービスも、標準CPU実装のRADMC-3Dをそのまま高速化する用途では優先候補になりません。

費用は「完成したモデル1件当たり」で比較する

参考として、2026年10月25日に確認したGoogle Cloudの米国アイオワ（us-central1）における通常のオンデマンド料金表では、c4-highcpu-16（16 vCPU／32 GiB）が0.680416米ドル／時間、c4-highcpu-96（96 vCPU／192 GiB）が4.082496米ドル／時間です。後者を10時間使う場合のVM本体料金は40.82496米ドル（約40.82米ドル）となります。

この金額は、追加ライセンス料のないLinux VMを10時間利用する場合のVM本体だけの計算例です。実測されたRADMC-3Dの計算費用ではありません。ストレージ、データ転送、IP、税金などは別途発生し得ます。リージョン、割引、クォータ、価格改定によっても変動します。料金は公式料金表で必ず再確認してください。

評価するのはvCPU単価だけではなく、出力の科学的妥当性を満たすモデル1件当たりの費用です。共有CPUと専有CPU、メモリ容量、起動とデータ転送の時間も含め、ローカルPCより有利になるかを判断します。予算通知は必ずしも支出を自動的に停止しないため、実行時間の上限と停止・削除手順を別途設定します。

初回試験の進め方

  1. ローカル環境を記録：RADMC-3Dのソース版、コンパイルオプション、CPU・RAM、入力と実行方法を確認し、公開して問題ない小規模なテストモデルを用意します。
  2. 手元で基準値を測定：OpenMPの1、2、4、8スレッドなどで壁時計時間、最大メモリ使用量、出力の変動を比較します。対象機能がOpenMP対応であることを確認します。
  3. 小規模クラウドVMで再現：16〜32 vCPU程度を候補として、同じソースと入力を用い、スレッド数ごとの実行時間と費用を測定します。最初から多数のVMを起動しません。
  4. 数値結果を検証：Monte Carloの乱数による統計変動を踏まえ、ダスト温度、SED、画像・スペクトルの整合性と収束性を確認します。バイナリが実行できただけで合格とはしません。
  5. 次の方法を選択：単一モデルの高速化が有効なら高性能VMを、多数モデルの処理が主目的ならBatchやジョブ配列を検討します。必要なら大学・研究機関のHPC共同利用も比較します。
  6. 課金資源を終了：結果と設定を安全に回収したあと、不要なVM、ディスク、固定IPなどの課金対象を確認して停止・削除します。

初回は予算を小さく設定し、速度、最大RAM、並列効率、費用、数値的一致度を一つの記録にまとめます。モデルや観測データが未公開の場合は、大学の規則、研究契約、クラウド事業者の取り扱い条件を確認してから転送します。

AIコーディング支援を使う範囲

Linuxのセットアップ、コンパイル条件の整理、ベンチマークスクリプト、ジョブ投入手順、ログ集計などは、AIコーディング支援の対象になります。ただし、SSHの秘密鍵やクラウドの認証情報をコード・公開リポジトリに入れないこと、課金を伴う操作は実行前に条件を確認すること、未公開研究データを無断で外部へ送らないことが必要です。

科学的な検証基準と物理的な解釈は研究者が定めます。AIによる環境整備の効率化と、数値解の正しさの検証は別の仕事です。

選択の目安

一つのモデルを短くしたい場合は、まずローカルでOpenMPの効果を測り、その後に単一の高性能CPU VMを比較します。モデルを数十〜数千件計算したい場合は、独立ジョブの設計とBatch／HPCクラスタが候補になります。結果の再現性、運用負担、接続性、調達条件と費用が折り合わなければ、大学・研究機関の共同利用計算機も有力です。

現時点では、ここに挙げた方法によるRADMC-3Dの実測はまだ行っていません。まず小規模な再現試験で性能と費用を測定し、その結果に基づいて必要な規模を決めるのが現実的です。
